## 0. 문서 개요와 사전 준비

### 0.1 목적과 사용법

각 파트는 독립적으로 실행 가능하도록 작성됐다. 단, 일부 시나리오는 다른 시나리오가
만든 데이터에 의존한다. 그런 경우 "사전 조건" 항목에 선행 시나리오를 명시했다.
예를 들어 "봉우리 생성" 시나리오는 식물이 하나 이상 있어야 하므로 "3.1을 수행 후
진행해 주세요"라고 표기한다.

테스트는 위에서 아래로 순서대로 진행하면 자연스럽게 데이터가 쌓이도록 목차를
배치했다. 특정 기능만 확인하려면 해당 시나리오의 사전 조건만 먼저 충족하면 된다.

### 0.2 실행 환경 준비

- 백엔드: `backend/` 에서 `poetry run python run.py` 실행 (http://localhost:8000)
- 프론트엔드: `frontend/` 에서 `npm run dev` 실행 (http://localhost:3000)
- 환경변수(`backend/.env`)에 `SUPABASE_URL`, `SUPABASE_JWT_SECRET`,
  `SUPABASE_SERVICE_ROLE_KEY`, `LLM_API_KEY`, `KEY_ENCRYPTION_SECRET` 설정
- 프론트(`frontend/.env.local`)에 `NEXT_PUBLIC_SUPABASE_URL`,
  `NEXT_PUBLIC_SUPABASE_ANON_KEY` 설정
- AI 채팅을 사용하려면 유효한 Gemini API 키가 있어야 한다. 사용자별 키는 설정
  페이지에서 입력하며, 없으면 `.env`의 `LLM_API_KEY`로 대체된다.

### 0.3 백엔드 재시작 주의사항

백엔드 코드(스킬, 프롬프트, 라우터, 권한, 타임존 등)를 변경한 뒤에는 반드시 서버를
수동 재시작해야 반영된다. uvicorn 자동 reload는 신뢰도가 낮다. 권장 절차는 모든
Python 프로세스 종료 후 `poetry run python run.py`를 다시 실행한다.
프론트엔드 변경은 브라우저 새로고침으로 반영된다.

### 0.4 계정 구분

- 일반 사용자: 로그인 후 `/home`으로 진입한다.
- 관리자: `profiles.role = "admin"` 인 계정은
  로그인 직후 `/admin`으로 자동 이동한다. 관리자 전용 페이지(`/admin/*`)는
  백엔드 `require_admin` 의존성과 프론트 가드로 이중 보호된다.

### 0.5 핵심 용어

- 식물(Plant): 분야 또는 카테고리. 예: 취업, 운동, 연애, 일상.
- 봉우리(Bud): 식물에 속한 구체적 고민 또는 일정. 씨앗 → 새싹 → 꽃 → 열매 →
  수확 생애주기를 가지며, 방치되면 시들음 → 썩음으로 전이된다.
- 일반 일정(Calendar Event): 봉우리가 아닌 순수 일정. 진행률·생애주기가 없으며
  `calendar_events` 테이블에 저장된다. 캘린더에만 표시된다.
- 스코프(세션): 채팅이 어떤 맥락에서 동작하는지를 나타낸다. global(전체),
  plant(특정 식물), bud(특정 봉우리), calendar(캘린더) 네 종류가 있다.
- 스킬(Skill): AI가 호출하는 도구. 데이터 생성·조회·수정·삭제를 수행한다.

## 1. AI 동작 원리 (배경 지식)

이 파트는 시연이 아니라 이후 시나리오의 "동작 원리"를 이해하기 위한 배경이다.

### 1.1 요청 처리 흐름과 ReAct 루프

사용자가 채팅을 보내면 `POST /chat/message`로 전달되고, `ChatOrchestrator.run()`이
동기 SSE(Server-Sent Events) 제너레이터로 응답을 스트리밍한다. 흐름은 다음과 같다.

1. 시스템 프롬프트 생성(`PromptBuilder.build_system`)
2. 대화 이력 조합(최근 20개) 후 사용자 발화 추가
3. ReAct 루프: LLM 호출 → 도구 사용(tool_use)이 있으면 해당 스킬 실행 →
   결과를 working_history에 추가 → 다시 LLM 호출. 최대 반복 횟수는 런타임 설정
   `llm_max_steps`(기본 10)에서 읽는다.
4. 텍스트 응답은 token 이벤트로 스트리밍

SSE 이벤트 종류: `start`, `tool_call`, `tool_result`, `token`, `done`, `error`.
프론트(`streamChat`)는 이 이벤트를 파싱해 화면에 반영하고, 스킬 실행 결과에 따라
TanStack Query 캐시를 무효화한다(`SKILL_INVALIDATIONS` 매핑).

### 1.2 시스템 프롬프트 구성

`PromptBuilder.build_system`은 매 요청마다 다음을 조합한다.

- 오늘 날짜: `rs.today()` 기준(KST). 1.5 참고.
- 현재 화면: 프론트가 보낸 `current_screen` (예: 홈, 캘린더)
- 스코프 컨텍스트 라인:
  - plant 스코프: "현재 상담 식물: {이름} (plant_id=...)"
  - bud 스코프: "현재 상담 세션: '{식물명}' 식물의 봉우리 '{봉우리 제목}' (bud_id=...)"
  - global / calendar: 별도 라인 없음
- 정원 현황: 활성 고민/일정 수, 시들음 수, 이번 달 수확 수
- 식물 목록(최대 10개, id 포함)
- 핵심 모델 설명(식물/봉우리/상태)
- 행동 원칙: 즉시 실행(확인 질문 금지), 의도 판단, 복합 작업 시 think 우선,
  삭제·포기는 명확한 의사가 있을 때만
- 행동 규칙: 일정 생성, 식물 생성, 봉우리 탐색(bud_id 필요 스킬 전 list_buds 강제),
  봉우리 생성, 봉우리 vs 캘린더 일정 선택, 일정 조회(두 종류 모두 확인),
  캘린더 화면 규칙, 세션별 권한, 세션 불일치 시 변경 제안
- 응답 형식: 스킬 실행 후 한두 문장으로 자연스럽게 안내

### 1.3 스킬 카탈로그와 호출 방식

등록된 스킬은 20개다(11번 파트 참고). 각 스킬은 이름, 설명, JSON 스키마(parameters)를
가지며, LLM에는 도구 목록(catalog)으로 전달된다. LLM이 function_call을 반환하면
`SkillRegistry.dispatch`가 해당 스킬의 `run(args, ctx)`를 실행한다. `ctx`(SkillContext)에는
user_id, db, 각 서비스 인스턴스, 그리고 현재 scope/scope_id가 담긴다.

### 1.4 스코프(세션)와 권한 모델

세션 권한은 `app/ai/permissions.py`에서 강제한다.

- global(전체): 모든 식물·봉우리·일정의 생성·조회·수정·삭제 가능
- plant(특정 식물): 해당 식물의 봉우리만 수정·삭제, 해당 식물만 삭제
- bud(특정 봉우리): 해당 봉우리만 수정·삭제
- calendar(캘린더): 일반 일정은 전체 권한, 봉우리(식물 일정)는 생성·조회만 가능하고
  수정·삭제 불가

생성과 조회는 모든 스코프에서 폭넓게 허용된다. 권한 가드는 기존 항목의 수정·삭제만
차단한다. 차단 시 스킬은 `ok=False, error_code="forbidden"`을 반환하고 AI가 그 사유를
사용자에게 안내한다.

**세션 태그 클릭 이동**: 채팅 패널 상단의 세션 태그(브레드크럼)에서 현재 세션이 아닌
태그를 클릭하면 그 세션으로 즉시 전환된다. 예) 봉우리 세션(`전체 › 🌿 식물명 › ● 봉우리`)
에서 `전체`를 누르면 global 세션, `🌿 식물명`을 누르면 그 식물 세션으로 이동한다. 전환
시 해당 세션의 대화 기록이 다시 로드되고 메인 화면(정원 캐러셀/상세)도 동기화된다.
활성(현재) 태그는 라벨이라 클릭되지 않는다.

### 1.5 타임존 처리 방식

런타임 설정 `app_timezone_offset_hours`(기본 9, KST)를 적용해 `rs.now()`와
`rs.today()`가 한국 시간 기준으로 계산된다. 프론트엔드는 브라우저 로컬(KST) 날짜로
일정을 저장하므로, 백엔드의 "오늘"도 KST여야 날짜가 어긋나지 않는다. 타임 트래블
오프셋(`time_offset_seconds`)은 이 위에 누적된다(9.14 참고).

## 2. 인증과 진입

### 2.1 Google 로그인

- 사전 조건: 없음. (Supabase 대시보드에 Google OAuth가 설정돼 있어야 한다.)
- 절차:
  1. `/login` 접속
  2. Google 로그인 버튼 클릭, 계정 선택 및 동의
- 기대 결과: 인증 성공 후 일반 사용자는 `/home`, 관리자는 `/admin`으로 이동한다.
- 동작 원리: Supabase Auth(`@supabase/supabase-js`)가 PKCE 콜백을 처리하고
  localStorage에 세션을 저장한다. `(app)/layout.tsx`의 `onAuthStateChange`가
  세션을 감지해 `/me`로 프로필을 가져오고, `role === "admin"`이면 `/admin`으로
  리다이렉트한다. 백엔드는 Supabase JWT를 JWKS(ES256, HS256 fallback)로 검증한다.

### 2.2 일반 사용자 진입과 관리자 진입

- 사전 조건: 2.1 수행 후 진행해 주세요.
- 절차: 로그인된 상태에서 `/home`과 `/admin`을 각각 주소창으로 접근
- 기대 결과: 일반 사용자가 `/admin`에 접근하면 `/home`으로 되돌려진다. 관리자는
  양쪽 모두 접근 가능하다.
- 동작 원리: `admin/layout.tsx`가 `user.role !== "admin"`이면 `/home`으로
  리다이렉트(useEffect 내). 백엔드 `require_admin`이 admin이 아닌 요청에 403을 반환한다.

## 3. 식물(Plant)

### 3.1 AI로 식물 생성

- 사전 조건: 없음.
- 절차:
  1. 사이드바의 AI 정원사 아이콘 또는 화면의 채팅 버튼으로 채팅을 연다(전체 세션).
  2. "취업 준비를 시작하려고 해" 와 같이 새 분야를 언급한다.
- 기대 결과: "취업" 식물이 생성됐다는 응답이 오고, 정원/홈에 새 식물이 나타난다.
- 동작 원리: 시스템 프롬프트의 "행동 규칙 > 식물 생성" 규칙에 따라 AI는 먼저
  `match_plant`로 유사 식물을 검색하고, 없으면 `create_plant`를 호출한다. 설명은
  문맥에서 추론해 채운다. "즉시 실행" 원칙으로 확인 질문 없이 진행한다.
  사용 스킬: match_plant → create_plant. 엔드포인트: 내부 서비스(PlantService.create).

### 3.2 정원 뷰와 리스트 뷰 조회

- 사전 조건: 3.1 수행 후 진행해 주세요. (식물이 1개 이상 필요)
- 절차:
  1. `/plants` 접속
  2. 상단 토글에서 정원/리스트를 전환
  3. 정원 뷰에서 키보드 좌우 방향키로 식물 사이를 이동
  4. 우측 하단 HUD의 `-`, 배율, `+` 버튼과 트랙패드 pinch로 `50%`~`200%`
     확대·축소 확인
  5. 봉우리가 없는 식물을 준비해 새싹 줄기 없이 화분만 표시되는지 확인
  6. 리스트 뷰에서 검색창에 식물명을 입력
- 기대 결과: 정원 뷰는 픽셀아트 캐러셀로, 리스트 뷰는 카드 그리드로 식물을 보여준다.
  리스트 검색은 이름·설명 부분 일치로 필터링한다. 축소된 빈 정원에서도 잔디 배경은
  오른쪽 끝까지 유지되고, 봉우리 0개 식물의 화분 바닥은 다른 화분과 같은 기준선에
  놓인다.
- 동작 원리: `GET /plants`로 목록을, `GET /buds`로 봉우리를 조회해 식물별로 묶는다.
  방향키 이동과 확대·축소 뒤 스크롤 위치는 배율을 반영해 보정한다. 픽셀 식물은
  `GardenPlantVisual.tsx`가 Figma `05 Plant Pixel Assets`의 no-pot extension 좌표로
  렌더링하며, 봉우리가 없으면 성장 레이어를 만들지 않는다.

### 3.3 식물 상세 화면

- 사전 조건: 3.1 수행 후 진행해 주세요.
- 절차:
  1. `/plants`에서 식물 카드를 클릭하거나 정원 뷰에서 선택 후 "상세" 클릭
  2. 상세 페이지에서 활성/수확/포기 통계와 봉우리 목록, 필터(전체/진행 중/완료) 확인
- 기대 결과: `/plants/{id}` 상세 페이지가 열리고 헤더 통계와 봉우리 목록이 표시된다.
- 동작 원리: `GET /plants/{id}`와 `GET /buds?plant_id={id}` 호출. 목록 캐시가 있으면
  헤더는 즉시 채워진다(initialData).

### 3.4 식물 삭제

- 사전 조건: 3.1 수행 후 진행해 주세요. 삭제 전용 식물을 하나 더 만들어 두는 것을 권장.
- 절차:
  1. 식물 상세 페이지에서 "식물 삭제" → "정말 삭제" 클릭
  2. 또는 전체 세션 채팅에서 "○○ 식물 삭제해줘"
- 기대 결과: 식물과 그 봉우리·기록이 삭제되고 정원으로 돌아간다.
- 동작 원리:
  - UI 경로: `DELETE /plants/{id}?hard=true`
  - AI 경로: `delete_plant` 스킬. "행동 원칙 > 삭제·포기" 규칙에 따라 명확한 삭제
    의사가 있을 때만 실행한다. 세션 권한(1.4): 전체 세션에서는 모든 식물 삭제 가능,
    특정 식물 세션에서는 그 식물만 삭제 가능(`can_delete_plant`).

## 4. 봉우리(Bud)

### 4.1 봉우리 생성 (고민 / 일정)

- 사전 조건: 3.1 수행 후 진행해 주세요. (관련 식물이 없으면 AI가 식물부터 만든다)
- 절차:
  1. 전체 세션 채팅에서 고민형: "면접에서 긴장하는 게 고민이야"
  2. 또는 일정형: "다음 주 월요일에 운동 가야 해"
- 기대 결과: 적절한 식물에 봉우리가 추가된다. 고민은 type=concern, 일정은
  type=schedule로 분류된다. 날짜가 있으면 deadline이 설정된다.
- 동작 원리: "행동 규칙 > 봉우리 생성"과 "일정·스케줄 생성" 규칙 적용. AI는
  match_plant로 식물을 찾고(없으면 create_plant) `create_bud`를 호출한다. type 분류와
  날짜 변환(YYYY-MM-DD), 시간 정보의 detail 저장은 프롬프트 규칙에 명시돼 있다.
  사용 스킬: match_plant → (create_plant) → create_bud.

### 4.2 봉우리 상세 드로어

- 사전 조건: 4.1 수행 후 진행해 주세요.
- 절차:
  1. 식물 상세 페이지에서 봉우리 행을 클릭
  2. 또는 `/plants` 정원에서 특정 봉우리 픽셀을 클릭
  3. 우측 드로어에서 진행률, 유형, 마감일, 생성일, 상태 변경 이력을 확인
- 기대 결과: 봉우리 상세 드로어가 열린다. 채팅이 열려 있으면 드로어가 채팅 옆으로 밀린다.
- 동작 원리: `GET /buds/{id}`로 봉우리와 히스토리를 조회. 드로어의 빠른 동작 버튼은
  채팅으로 자체 완결형 지시를 전달한다(아래 4.3~4.7). 정원 봉우리 픽셀은
  `/plants/{plantId}?bud={budId}`로 이동해 같은 drawer를 즉시 연다. 마우스를 올리면
  봉우리 이름 툴팁을 표시한다.

### 4.3 진행률 변경과 자동 상태 전이

- 사전 조건: 4.1 수행 후 진행해 주세요.
- 절차:
  1. 봉우리 상세 드로어에서 "+20%" 버튼 클릭, 또는
  2. 채팅에서 "○○ 봉우리 진행률 70%로 올려줘"
- 기대 결과: 진행률이 갱신되고, 임계값(30/60/85%)을 넘으면 상태가 자동 전이된다
  (30 이상 새싹, 60 이상 꽃, 85 이상 열매).
- 동작 원리: `update_bud_progress` 스킬. bud_id를 모르면 "봉우리 탐색" 규칙에 따라
  먼저 `list_buds`를 호출한다. 자동 전이 임계값은 BudService에 정의돼 있다.
  세션 권한(1.4): 해당 봉우리/식물 세션 또는 전체 세션에서만 수정 가능.

### 4.4 상태 직접 변경

- 사전 조건: 4.1 수행 후 진행해 주세요.
- 절차: 채팅에서 "○○ 봉우리를 꽃 단계로 바꿔줘"
- 기대 결과: 상태가 지정 단계로 변경되고 이력에 기록된다.
- 동작 원리: `update_bud_status` 스킬(상태 enum: seed/bud/flower/fruit/harvested/
  wilting/rot). 호출 전 list_buds로 bud_id 확보. 권한 가드 적용.

### 4.5 마감일 설정

- 사전 조건: 4.1 수행 후 진행해 주세요.
- 절차: 채팅에서 "○○ 봉우리 마감일을 이번 주 금요일로 잡아줘"
- 기대 결과: 마감일이 설정되고, 캘린더에 식물 일정으로 표시된다(5.2 참고).
- 동작 원리: `set_deadline` 스킬. 날짜는 YYYY-MM-DD로 변환된다(상대 표현은 오늘
  기준으로 계산, 오늘은 KST). 권한 가드 적용.

### 4.6 수확 처리

- 사전 조건: 4.1 수행 후 진행해 주세요.
- 절차: 드로어의 "수확" 버튼, 또는 채팅에서 "○○ 끝냈어, 수확 처리해줘"
- 기대 결과: 봉우리가 harvested 상태가 되고 통계의 수확 수가 증가한다.
- 동작 원리: `harvest_bud` 스킬. 권한 가드 적용.

### 4.7 포기 처리

- 사전 조건: 4.1 수행 후 진행해 주세요.
- 절차: 드로어의 "포기" 버튼, 또는 채팅에서 "○○ 그만둘래, 포기 처리해줘"
- 기대 결과: 봉우리가 rot(포기) 상태가 된다.
- 동작 원리: `abandon_bud` 스킬. "삭제·포기" 원칙에 따라 명확한 의사가 있을 때만
  실행한다. 권한 가드 적용.

### 4.8 진행률 수동 조절 (슬라이더) + 사유 팝업

- 사전 조건: 4.1 수행 후 진행해 주세요. (완료/포기 상태가 아닌 봉우리 필요)
- 절차:
  1. 식물 상세 페이지에서 봉우리를 클릭해 상세 드로어를 연다.
  2. "진행률 (완성도)" 슬라이더를 드래그해 값을 바꾸고 손을 뗀다.
  3. "왜 변경하였나요? AI 정원사가 도움을 줄 수 있어요" 팝업에서 사유를 입력
  4. "AI에게 전달" 또는 "그냥 저장"을 선택 (배경 클릭은 취소)
- 기대 결과:
  - 진행률이 즉시 저장되고, 30/60/85% 임계값을 넘으면 상태가 자동 전이된다.
  - "AI에게 전달"을 누르면 봉우리(bud) 세션 채팅이 열리며 "방금 진행률을 X%로
    변경했어요. 이유: ..." 메시지가 자동 전송되어 AI가 조언한다(진행률을 다시
    바꾸지는 않는다).
  - "그냥 저장"은 사유 없이 진행률만 저장한다.
- 동작 원리: 슬라이더를 놓는 순간(onPointerUp/onKeyUp) 값이 바뀌었으면 팝업이
  뜬다. 저장은 `PATCH /buds/{id}/progress {progress, note}` → BudService.update_progress로
  처리되어 AI 스킬과 동일한 자동 전이·이력 기록을 거친다(0~100 clamp). "AI에게
  전달"은 chatStore의 pendingSend로 사유 포함 프롬프트를 bud 세션에 자동 전송한다.
  이 흐름은 "사용자가 왜 바꿨는지 AI가 알아야 한다"는 요구를 충족한다.
  - 참고: 완료(harvested)·포기(rot) 상태 봉우리는 슬라이더 대신 정적 진행률 바를
    표시한다.

## 5. 캘린더

### 5.1 일정 직접 추가 (모달 폼)

- 사전 조건: 관련 식물을 연결하려면 3.1을 먼저 수행하면 좋다(식물 없이도 추가 가능).
- 절차:
  1. `/calendar` 접속
  2. 우측 하단 "일정 추가" 클릭
  3. 모달에서 제목, 날짜, 관련 식물(선택), 세부 정보, 색상 입력 후 "추가"
- 기대 결과: 봉우리를 만들지 않고 일반 일정만 추가된다. 캘린더 격자와 선택일 목록에
  표시된다.
- 동작 원리: `POST /calendar/events {title, date, plant_id?, detail, color?}`. 일반 일정은
  `calendar_events` 테이블에 저장되며 봉우리 생애주기가 없다. 이 테이블은 PostgREST
  스키마 캐시 문제로 `exec_admin_query` RPC를 통해 접근한다(주입 방지 위해 값
  이스케이프). 일정은 source="event"로 표시된다. 색상은 6개 팔레트 ID 중 하나이며
  생략 시 기존 강조색과 같은 olive를 사용한다.

### 5.2 봉우리 마감 일정 표시

- 사전 조건: 4.5 수행 후 진행해 주세요. (마감일이 있는 봉우리 필요)
- 절차: `/calendar`에서 해당 날짜 확인
- 기대 결과: 봉우리의 마감일이 캘린더에 표시된다. 클릭하면 그 식물 상세로 이동한다.
- 동작 원리: `GET /calendar?from=&to=`가 봉우리 deadline과 일반 일정을 병합해
  반환한다. 봉우리 유래 항목은 source="bud", 일반 일정은 source="event"이며 프론트는
  점 색상과 배지로 구분한다. 봉우리 항목은 상태 색상, 일반 일정은 사용자가 고른
  팔레트 색상을 쓴다.

### 5.3 AI 일정 제안 버튼 (실제 AI 호출)

- 사전 조건: 없음. (일정이 있으면 더 풍부한 응답을 받는다. 5.1을 먼저 권장)
- 절차:
  1. `/calendar` 우측 "AI 일정 제안" 카드에서 "오늘 일정 물어보기" 클릭
- 기대 결과: 캘린더 세션 채팅이 열리고 "오늘 일정 설명해줘"가 실제 전송되어 AI가
  스트리밍 응답한다(고정 문구가 아님).
- 동작 원리: 버튼이 `openWith({kind:"calendar"}, {send:"오늘 일정 설명해줘"})`를
  호출한다. chatStore의 pendingSend가 설정되고, ChatPanel은 새 세션 이력 로드 후
  자동으로 그 문장을 전송한다. 이후 AI는 "일정 조회" 규칙(5.4)을 따른다.

### 5.4 일반 일정 조회 (AI)

- 사전 조건: 5.1 수행 후 진행해 주세요.
- 절차: 캘린더 세션 채팅에서 "내 일정 알려줘" 또는 "오늘 일정 설명해줘"
- 기대 결과: AI가 일반 일정과 식물 일정을 구분하여 설명한다.
- 동작 원리: "행동 규칙 > 일정 조회" 규칙에 따라 AI는 `list_buds`(식물 일정)와
  `list_calendar_events`(일반 일정)를 모두 호출한 뒤, 두 종류를 나누어 안내한다.
  list_calendar_events는 기간 미지정 시 최근 30일부터 1년 후까지를 조회한다.

### 5.5 일반 일정 수정 (AI)

- 사전 조건: 5.1 수행 후 진행해 주세요.
- 절차: 캘린더 세션 채팅에서 "○○ 일정을 다음 주 화요일로 옮겨줘" 또는 제목/세부 변경 요청
- 기대 결과: 해당 일반 일정이 수정된다.
- 동작 원리: AI가 먼저 `list_calendar_events`로 event_id를 찾고
  `update_calendar_event`를 호출한다. 권한(1.4): 일반 일정 수정은 캘린더 세션 또는
  전체 세션에서만 가능(`can_modify_calendar_event`). 엔드포인트:
  `PATCH /calendar/events/{id}`.

### 5.6 일반 일정 삭제 (AI 또는 UI)

- 사전 조건: 5.1 수행 후 진행해 주세요.
- 절차:
  1. UI: 캘린더 선택일 목록 또는 오늘 일정 목록에서 일반 일정의 삭제(X) 버튼 클릭
  2. AI: 캘린더 세션 채팅에서 "○○ 일정 삭제해줘"
- 기대 결과: 일반 일정이 삭제된다. 봉우리 유래 일정에는 삭제 버튼이 없다.
- 동작 원리:
  - UI: `DELETE /calendar/events/{id}`
  - AI: `list_calendar_events` → `delete_calendar_event`. 권한은 5.5와 동일.
    봉우리 일정은 캘린더 세션에서 수정·삭제 불가(1.4).

### 5.7 오늘 일정과 타임존 확인

- 사전 조건: 5.1에서 일정을 "오늘" 날짜로 추가 후 진행해 주세요.
- 절차: 캘린더 세션에서 "오늘 일정 설명해줘"
- 기대 결과: 방금 추가한 오늘 일정이 빠짐없이 조회된다.
- 동작 원리: 백엔드 "오늘"이 KST(`rs.today()`)로 계산되어 프론트가 저장한 로컬 날짜와
  일치한다(1.5). 과거에는 UTC 기준이라 자정 무렵 하루가 어긋나 오늘 일정이 누락됐다.

## 6. 채팅 명령어

채팅 입력창에 "/"를 입력하면 명령어 팔레트가 뜬다. 명령어는 프론트(ChatPanel)에서
처리되며 일부는 AI 호출로 이어진다.

### 6.1 /skills

- 사전 조건: 없음.
- 절차: 채팅에 `/skills` 입력
- 기대 결과: 사용 가능한 스킬 목록 카드가 화면에 표시된다.
- 동작 원리: 프론트의 정적 목록(SKILLS_INFO)을 렌더링한다. AI 호출 없음.

### 6.2 /plants

- 사전 조건: 3.1 수행 후 진행하면 결과를 더 잘 확인할 수 있다.
- 절차: 채팅에 `/plants` 입력
- 기대 결과: 식물 목록 카드가 표시되고, 각 항목에서 상담/보기로 이동할 수 있다.
- 동작 원리: 프론트가 `GET /plants`(listPlants)를 호출해 카드로 렌더링한다. AI 호출 없음.

### 6.3 /use

- 사전 조건: 없음.
- 절차: `/use get_garden_briefing` 처럼 `/use 스킬명` 입력
- 기대 결과: 지정한 스킬을 즉시 실행하도록 AI에 요청이 전달된다.
- 동작 원리: 프론트가 "○○ 스킬을 지금 바로 실행해줘"라는 발화를 sendText로 전송하고,
  AI가 해당 스킬을 호출한다. 인자가 필요하면 AI가 한 가지만 되묻는다.

### 6.4 /new

- 사전 조건: 없음.
- 절차: 채팅에 `/new` 입력
- 기대 결과: AI가 봉우리 생성을 위한 항목(식물, 제목, 유형, 세부, 마감)을 한 단계씩
  물어보며 수집한 뒤 create_bud를 호출한다.
- 동작 원리: 프론트가 안내형 지시문을 sendText로 전송한다. 이 경우에 한해 AI는
  순차 질문을 한다(평소 "질문 금지"의 예외).

### 6.5 /compact

- 사전 조건: 채팅에 메시지가 어느 정도 쌓인 뒤 진행해 주세요.
- 절차: 채팅에 `/compact` 입력
- 기대 결과: 지금까지 대화를 핵심 3~5문장으로 요약한다.
- 동작 원리: 프론트가 화면의 대화 텍스트를 모아 요약 요청 발화를 AI에 전송한다.

### 6.6 /clear

- 사전 조건: 없음.
- 절차: 채팅에 `/clear` 입력
- 기대 결과: 현재 화면의 대화 내용만 비워진다. 저장된 기록(DB)은 유지된다.
- 동작 원리: 프론트 상태(messages)만 초기화한다. 서버 호출 없음. 새로고침하거나
  세션을 다시 열면 기록이 다시 로드된다.

### 6.7 /delete

- 사전 조건: 없음.
- 절차:
  1. 채팅에 `/delete` 입력
  2. 확인 창에서 동의
- 기대 결과: 현재 세션(스코프)의 대화 기록이 DB에서 완전히 삭제된다. 화면도 비워지고
  기록 페이지(/history)에서도 사라진다.
- 동작 원리: 확인 후 `DELETE /conversations?scope=&scope_id=` 호출. 대화와 메시지가
  CASCADE로 삭제된다. /clear(화면만)와 구분된다.

### 6.8 /settings

- 사전 조건: 없음.
- 절차: 채팅에 `/settings` 입력
- 기대 결과: 설정 페이지로 이동한다.
- 동작 원리: 채팅을 닫고 `/settings`로 라우팅한다.

## 7. 세션(스코프) 시스템

### 7.1 페이지에 따른 세션 자동 설정

- 사전 조건: 없음.
- 절차:
  1. `/home` 또는 `/plants`로 이동한 뒤 채팅을 연다.
  2. `/calendar`로 이동한 뒤 채팅을 연다.
- 기대 결과: 홈·정원에서는 전체(global) 세션, 캘린더에서는 calendar 세션으로 설정된다.
- 동작 원리: `(app)/layout.tsx`가 경로 변화를 감지해 `setScope`를 호출한다. 홈·정원은
  global, 캘린더는 calendar. 식물 상세/기록/설정 페이지는 현재 스코프를 유지한다.
  경로가 바뀔 때만 동작하므로 같은 페이지에서 "상담" 버튼으로 식물 세션에 진입하는
  것과 충돌하지 않는다.

### 7.2 식물 세션에서의 수정/삭제 권한

- 사전 조건: 서로 다른 두 식물(예: 운동, 연애)과 각 봉우리가 필요. 3.1과 4.1을
  서로 다른 분야로 두 번 수행 후 진행해 주세요.
- 절차:
  1. 운동 식물 상세 페이지에서 "이 식물 상담"으로 운동 세션을 연다.
  2. 운동 식물의 봉우리에 대해 "진행률 올려줘" 등 수정 요청 → 정상 처리 확인
  3. 같은 세션에서 연애 식물의 봉우리를 수정 요청 → 차단/세션 변경 권유 확인
- 기대 결과: 현재 식물의 봉우리는 수정되고, 다른 식물의 봉우리 수정은 거부되거나
  세션 변경을 권유받는다.
- 동작 원리: `guard_bud`가 bud의 plant_id와 현재 plant 스코프를 비교한다. 불일치 시
  forbidden. 동시에 프롬프트의 "세션 불일치" 규칙에 따라 AI는 수정 대신 변경을
  제안하려 한다(7.3).

### 7.3 세션 불일치 감지와 변경 권유, 입력 이관

- 사전 조건: 7.2와 동일하게 두 분야의 식물·봉우리가 필요. 3.1과 4.1을 두 분야로
  수행 후 진행해 주세요.
- 절차:
  1. 운동 식물(또는 봉우리) 세션을 연다.
  2. 다른 분야 발화를 한다. 예: 운동 세션에서 "면접 준비가 걱정돼"
  3. 표시되는 "대화 세션을 변경해 드릴까요?" 배너에서 "변경하기" 클릭
  4. 새 세션 입력창에 직전 질문이 채워진 것을 확인하고 엔터
- 기대 결과: 관련 식물(취업 등) 세션으로 전환되고, 직전 질문이 입력창에 그대로
  옮겨진다. 엔터만 누르면 올바른 세션에서 실행된다.
- 동작 원리: 프롬프트 "세션 불일치 → 세션 변경 제안" 규칙에 따라 AI는 현재 세션에서
  실행하지 않고 `match_plant`로 관련 식물을 찾은 뒤 `suggest_scope_change`만 호출한다.
  프론트는 그 결과로 배너를 띄우고, 직전 사용자 발화를 carryText로 보관한다. "변경하기"는
  `openWith(targetScope, {prefill: carryText})`를 호출해 새 세션으로 이동하면서 입력창을
  채운다(전송은 사용자 엔터로). bud 세션에서도 동일하게 동작한다(7.4).

### 7.4 봉우리 세션에서의 불일치 감지

- 사전 조건: 7.3과 동일. 3.1과 4.1을 두 분야로 수행 후 진행해 주세요.
- 절차:
  1. 한 봉우리(예: 연애 식물의 어떤 봉우리) 세션을 연다.
  2. 다른 분야 발화(예: 운동/근육통)를 한다.
- 기대 결과: 현재 봉우리 세션이 어떤 식물·주제인지 인지하고, 다른 분야면 세션 변경을
  제안한다.
- 동작 원리: bud 스코프에서는 orchestrator가 현재 봉우리를 조회해 그 식물명과 봉우리
  제목을 프롬프트에 넣는다("현재 상담 세션: '연애' 식물의 봉우리 '...'"). 이 컨텍스트가
  없던 과거에는 bud_id만 알아 불일치를 감지하지 못했다.

### 7.5 캘린더 세션 권한 (봉우리 생성/조회만)

- 사전 조건: 4.1 수행 후 진행해 주세요. (수정·삭제 대상 봉우리 필요)
- 절차:
  1. `/calendar`에서 채팅을 연다(캘린더 세션).
  2. 봉우리 조회: "내 봉우리 일정 보여줘" → 조회 가능
  3. 봉우리 생성: "운동 식물에 스트레칭 봉우리 추가해줘" → 생성 가능
  4. 봉우리 수정·삭제: "○○ 봉우리 수확 처리해줘" → 거부/안내 확인
- 기대 결과: 캘린더 세션에서 봉우리는 생성·조회만 되고, 수정·삭제는 거부된다.
  일반 일정은 모든 작업이 가능하다(5.5, 5.6).
- 동작 원리: `can_modify_bud`가 calendar 스코프의 봉우리 수정·삭제를 차단(forbidden)한다.
  생성(create_bud)과 조회(list_buds)는 허용된다.

### 7.6 세션 변경 시 메인 화면 동기화

- 사전 조건: 7.3 수행 후 진행해 주세요.
- 절차:
  1. 정원(`/plants`)을 보면서 세션을 특정 식물로 변경 → 캐러셀이 그 식물로 이동하는지 확인
  2. 식물 상세 페이지에서 세션 변경 배너로 다른 식물로 전환 → 그 식물 상세로 이동하는지 확인
- 기대 결과: 정원 뷰에서는 캐러셀이 해당 식물을 중앙에 표시하고, 상세 페이지에서는
  변경된 식물의 상세 화면으로 이동한다.
- 동작 원리: 정원 페이지는 scope.id에 맞춰 selectedIdx를 갱신한다. 상세 페이지는
  세션 id의 "실제 변화"를 ref로 감지해 그 식물 상세로 이동한다. 단순히 스코프와 페이지가
  다르다는 이유로는 이동하지 않으므로(과거 회귀), 예전 세션이 열린 채 다른 식물을
  탐색하는 동작은 가로채지 않는다.

## 8. 알림

### 8.1 자동 알림 발생 (시들 / 썩음 / 마감 임박)

- 사전 조건: 관리자 계정 필요. 4.1과 4.5로 봉우리·마감일을 만든 뒤 진행해 주세요.
- 절차:
  1. 관리자로 `/admin/controller` 접속
  2. 타임 트래블에서 시간을 충분히(예: +14일) 이동(9.14 참고)
  3. 이동 시 자동 전환 스캔이 실행됨. 또는 "전환 스캔 즉시 실행" 클릭
  4. 일반 사용자 화면 사이드바의 알림 종 아이콘 확인
- 기대 결과: 오래 방치된 봉우리는 시들음 → 썩음으로 전이되고, 마감 임박 봉우리에는
  마감 경고 알림이 생성된다.
- 동작 원리: TransitionService가 `rs.now()/today()`(타임 트래블 반영) 기준으로 wilting/rot
  전이와 deadline 경고를 계산해 notifications에 push한다. 알림 종류:
  bud_wilting, bud_rot, deadline_warning.

### 8.2 알림 상세 보기와 전체 기록 탭

- 사전 조건: 8.1 또는 9.4로 알림이 1개 이상 생성된 뒤 진행해 주세요.
- 절차:
  1. 사이드바 알림 종 아이콘 클릭
  2. "안 읽음" / "전체 기록" 탭 전환
  3. 알림 항목 클릭 → 상세(전체 메시지, 정확한 시각) 펼침 확인
- 기대 결과: 안 읽은 알림과 전체 기록(읽은 것 포함)을 볼 수 있고, 클릭하면 상세가
  펼쳐진다. 관리자 메시지(공지/경고 등)는 본문이 그대로 표시된다.
- 동작 원리: `GET /notifications`(안 읽음)와 `GET /notifications?include_read=true`(전체).
  관리자 메시지는 payload.message를 본문으로 렌더링한다(과거에는 종류명만 보였음).

### 8.3 모두 읽음 처리

- 사전 조건: 8.2 수행 후 진행해 주세요.
- 절차: 알림 팝오버에서 "모두 읽음" 클릭
- 기대 결과: 안 읽은 알림이 모두 읽음 처리되고 배지 수가 0이 된다.
- 동작 원리: `POST /notifications/ack-all`(단일 요청). 개별 읽음은 항목의 X 버튼으로
  `POST /notifications/{id}/ack`.

### 8.4 실시간 표시 (폴링)

- 사전 조건: 9.4로 관리자가 알림을 발송한 직후 진행해 주세요.
- 절차: 일반 사용자 화면을 새로고침하지 않고 약 15초 대기
- 기대 결과: 새로고침 없이 약 15초 내에 배지 수가 자동 증가한다.
- 동작 원리: Sidebar의 알림 쿼리가 15초 간격으로 폴링한다(refetchInterval, 백그라운드
  포함). 팝오버가 열려 있으면 목록도 15초 간격으로 갱신된다.

### 9.3 AI 로그 브라우저

- 사전 조건: AI 채팅을 한 번 이상 사용한 뒤 진행해 주세요(3.1 등).

- 기대 결과: 시스템 프롬프트, LLM 호출 내역, 스킬 호출, 이벤트가 슬라이드 패널에 표시된다.
- 동작 원리: `GET /admin/logs`(목록), `GET /admin/logs/{filename}`(상세). 각 채팅은
  `backend/logs/chat/`에 JSON으로 기록된다. 대화 기록(DB)과는 별개의 저장소다.
- **LLM 오류 표시**: Gemini 호출이 실패한 세션은 목록 테이블 `상태` 칸에 빨간
  `오류 N` 배지가 뜨고, 상세 패널에 빨간 `오류 (N)` 탭이 추가된다. 탭을 열면 오류
  종류 배지(서버 과부하 503 / 한도 초과 429 / 인증 / 모델 없음 404 / 시간 초과 /
  기타), 한국어 원인, 그리고 Gemini가 던진 원문(upstream)이 표시된다.
- 동작 원리: `llm_client`가 실패 시 `error`/`error_kind`/`error_cause`를 반환 →
  `log_recorder.log_llm_error()`가 세션 로그의 `llm_errors[]`에 누적 → 관리자 API가
  `error_count`/`error_kind`/`last_error`로 노출. "AI 모델이 일시적으로 혼잡합니다"는
  대부분 무료/공유 티어의 503 서버 과부하이며 보통 자동 해소된다(12.1 재시도 참고).

### 9.4 알림 발송

- 절차:
  1. `/admin/notifications`에서 유형 선택(일반/공지/경고)
  2. 수신 대상 선택(전체 또는 특정 사용자)
  3. 메시지 입력 후 발송
- 기대 결과: 대상자에게 알림이 생성되고 발송 내역에 표시된다. 수신자는 8.2처럼 본문을
  확인할 수 있다.
- 동작 원리: `POST /admin/notifications {user_ids, kind, message}`. user_ids가 비면
  전체 발송. payload.from_admin=true로 표시되어 발송 내역(`GET /admin/notifications/history`)에서
  필터된다.

### 9.5 데이터 관리 - 개별 삭제

- 사전 조건: 대상 사용자에게 대화/식물/봉우리 데이터가 있어야 한다. 3.1, 4.1 수행 후 진행.
- 절차:
  1. `/admin/data`에서 사용자 카드를 펼친다.
  2. 대화 기록 / 식물 / 봉우리 탭에서 개별 항목의 삭제 클릭, 재확인 모달 동의
- 기대 결과: 선택 항목만 삭제된다(식물 삭제 시 봉우리·기록 CASCADE).
- 동작 원리: `DELETE /admin/data/conversations/{id}`, `.../plants/{id}`, `.../buds/{id}`.
  목록 조회는 bulk 쿼리로 메시지/봉우리 수를 집계한다.

### 9.6 데이터 관리 - 전체 일괄 삭제

- 절차:
  1. `/admin/data` 상단 "전체 일괄 작업"
  2. "전체 대화 기록 삭제(DB)" 또는 "AI 로그 파일만 삭제" 중 선택, 재확인 동의
- 기대 결과: 선택에 따라 DB 대화 또는 로그 파일만 삭제된다. 둘은 명확히 구분된다.
- 동작 원리: `DELETE /admin/controller/conversations/all`(DB),
  `DELETE /admin/controller/logs/all`(파일). 대화 기록(DB, /history에 표시)과 AI 로그
  파일(관리자 로그 페이지에 표시)은 별개 저장소다.

### 9.7 회원 계정 완전 삭제

- 사전 조건: 테스트용 비관리자 계정을 대상으로 진행해 주세요(되돌릴 수 없음).
- 절차: `/admin/data`의 사용자 카드에서 "계정 삭제" → 재확인 동의
- 기대 결과: 해당 사용자의 식물·봉우리·대화·정원 상태·알림·AI 로그 파일과 Supabase
  Auth 계정까지 모두 삭제된다.
- 동작 원리: `DELETE /admin/controller/users/{id}/account` → UserService.delete_account.
  user_id 기준 bulk 삭제 + CASCADE + 로그 파일 삭제 + Supabase Auth admin 삭제.

### 9.8 데이터 백업 생성

- 절차: `/admin/data`의 "데이터 백업 / 복원"에서 "지금 백업 생성" 클릭
- 기대 결과: 전체 테이블을 압축한 백업 파일(backup_YYYYMMDD_HHMMSS.zip)이 목록에
  추가된다(행 수·크기·생성 시각 표시).
- 동작 원리: `POST /admin/backup` → BackupService.create_backup. 8개 테이블(profiles,
  plants, buds, bud_history, garden_state, conversations, conversation_messages,
  notifications)을 페이징 덤프해 ZIP으로 저장한다. ZIP 안에는 목록 조회용 meta.json과
  전체 데이터 data.json이 들어간다.

### 9.9 데이터 복원 (덮어쓰기 방지)

- 사전 조건: 9.8 수행 후 진행해 주세요. (복원할 백업 파일 필요)
- 절차:
  1. 백업 목록에서 항목의 "복원" 클릭, 재확인 동의
  2. 복원 결과 리포트(테이블별 추가/건너뜀/실패) 확인
- 기대 결과: 백업의 데이터가 현재 DB로 들어오되, 이미 존재하는 항목(동일 PK)은
  덮어쓰지 않고 건너뛴다. 새 항목만 추가된다.
- 동작 원리: `POST /admin/backups/{filename}/restore` → BackupService.restore_backup.
  FK 의존 순서(부모 먼저)로 복원하며, 각 테이블에서 기존 id를 조회해 없는 행만 insert한다.

### 9.10 백업 다운로드와 삭제

- 사전 조건: 9.8 수행 후 진행해 주세요.
- 절차: 백업 목록에서 "다운로드"로 ZIP을 내려받거나, "삭제"로 파일 제거(재확인)
- 기대 결과: ZIP이 브라우저로 저장되거나 목록에서 제거된다.
- 동작 원리: 다운로드는 `GET /admin/backups/{filename}/download`를 Bearer 토큰과 함께
  fetch해 Blob으로 저장한다(downloadFile 헬퍼). 삭제는 `DELETE /admin/backups/{filename}`.

### 9.11 컨트롤러 - 런타임 설정

- 절차: `/admin/controller`의 "런타임 설정"에서 값(예: llm_default_model,
  llm_max_steps, default_wilting_days, app_timezone_offset_hours 등)을 인라인 수정.
  필요 시 "디스크에 저장"으로 영속화
- 기대 결과: 설정이 즉시 반영되고, 디스크 저장 시 재시작 후에도 유지된다.
- 동작 원리: `GET/PATCH /admin/controller/settings`. 값은 인메모리 저장소
  (runtime_settings)에 보관되며, save 시 JSON 스냅샷으로 기록된다. 다수의 동작
  (모델, ReAct 스텝, 전이 일수, 타임존)이 이 값을 즉시 읽는다.

### 9.12 컨트롤러 - 사용자별 AI 모델

- 절차: "사용자별 AI 모델 오버라이드"에서 특정 사용자의 모델을 변경
- 기대 결과: 해당 사용자의 채팅이 지정 모델로 처리된다.
- 동작 원리: `PATCH /admin/controller/users/{id}/model`로 profiles.ai_model 갱신.
  채팅 시 사용자 모델이 있으면 우선, 없으면 런타임 기본 모델을 사용한다
  (`user_model or global_model`).
- **선택 가능 모델**: 드롭다운은 백엔드 `runtime_settings.AVAILABLE_MODELS`를 그대로
  렌더링한다(기본 모델 9.11과 동일 목록 공유). 최신순으로 `gemini-3.5-flash`,
  `gemini-3.1-pro`, `gemini-3-pro`, `gemini-3-flash`, `gemini-2.5-pro`,
  `gemini-2.5-flash`, `gemini-2.5-flash-lite` + 레거시(2.0/1.5/1.0). 두 엔드포인트
  모두 `require_admin`(관리자 전용)이며, per-user는 이 목록으로 화이트리스트 검증한다.
- 참고: 3.x/3.5 모델 ID는 Google 명명 규칙 추정값으로, 아직 API가 서빙하지 않으면
  해당 모델로 대화 시 9.3의 AI 로그에 `모델 없음 (404)` 오류로 표시된다.

### 9.13 컨트롤러 - SQL 실행기

- 절차: "SQL 실행기"에 쿼리 입력 후 실행(Ctrl+Enter). 예: `select id, email from profiles limit 5`
- 기대 결과: SELECT는 결과 테이블, DML/DDL은 영향 행 수가 표시된다.
- 동작 원리: `POST /admin/controller/sql` → `exec_admin_query` RPC(SECURITY DEFINER).
  관리자 전용이며 모든 실행은 admin user_id와 쿼리로 감사 로깅된다.

### 9.14 컨트롤러 - 타임 트래블

- 절차:
  1. "서버 시간 이동"에서 빠른 버튼(+1일, +7일 등) 또는 직접 입력으로 시간 이동
  2. 실제/가상 두 시계를 비교, 이동 후 자동 전환 스캔 결과 확인
  3. "리셋"으로 실제 시간 복귀
- 기대 결과: 가상 서버 시간이 이동하고, 시들음/썩음/마감 경고가 그 시점 기준으로 처리된다.
- 동작 원리: `GET/PATCH /admin/controller/time`. time_offset_seconds가 변경되면
  `rs.now()/today()`가 KST 기준 시간에 그 오프셋을 더해 계산한다. 이동 후 TransitionService
  스캔이 자동 실행된다. 데모/테스트 전용 기능이다.

### 9.15 컨트롤러 - 스케줄러 즉시 실행

- 절차: 상단의 "전환 스캔 즉시 실행" 클릭
- 기대 결과: 전이 스캔이 즉시 1회 실행된다.
- 동작 원리: `POST /admin/controller/scheduler/trigger` → TransitionService.scan_all.
  평소에는 APScheduler가 `scheduler_interval_minutes`(기본 10분) 간격으로 실행한다.

## 11. AI 스킬 전체 레퍼런스 (20개)

각 스킬의 트리거 발화 예시와 동작이다. 권한이 적용되는 변이 스킬은 표기했다.

조회/계획 스킬:
- think: 복잡한 작업 전 계획 수립(데이터 변경 없음). 복합 작업 시 먼저 호출.
- match_plant: 분야와 유사한 기존 식물 검색. 생성 전 중복 방지용.
- list_plants: 식물 목록 조회. 예 "내 식물 보여줘".
- list_buds: 봉우리 목록 조회. bud_id가 필요한 스킬 전에 선행 호출.
- get_statistics: 정원 통계 조회.
- get_garden_briefing: 오늘의 정원 브리핑 문장 생성.
- search_conversation: 대화 로그 검색(LIKE, 와일드카드 이스케이프 적용).
- list_calendar_events: 일반 일정(봉우리 아님) 조회. 기간 미지정 시 최근 30일~1년 후.

생성 스킬:
- create_plant: 새 식물 생성. match_plant 후 호출.
- create_bud: 봉우리(고민/일정) 생성. 예 "면접 준비 봉우리 추가".
- create_calendar_event: 일반 일정 생성(봉우리 없이). 예 "다음 주 화요일 치과 예약".

변이 스킬(권한 가드 적용):
- update_bud_progress: 진행률 변경 + 자동 상태 전이.
- update_bud_status: 상태 직접 변경.
- set_deadline: 마감일 설정.
- harvest_bud: 수확(완료).
- abandon_bud: 포기(rot).
- delete_plant: 식물 삭제/보관(can_delete_plant).
- update_calendar_event: 일반 일정 수정(can_modify_calendar_event, 캘린더/전체 세션).
- delete_calendar_event: 일반 일정 삭제(동일 권한).

세션 보조 스킬:
- suggest_scope_change: 현재 세션과 다른 분야 요청 시 세션 변경 제안 UI를 띄운다
  (plant/bud 세션에서만, global/calendar에서는 호출하지 않음).

각 스킬은 6.1의 /skills 명령이나 6.3의 /use 명령으로 직접 확인·실행할 수 있다.

## 12. 안정성 / 회귀 확인 항목

### 12.1 LLM 과부하 자동 재시도

- 사전 조건: 없음(과부하는 외부 요인이라 재현이 어려울 수 있다).
- 확인 포인트: Gemini가 503(UNAVAILABLE/high demand)을 반환해도 즉시 오류로 끝나지
  않고 지수 백오프(1초, 2초)로 최대 3회 재시도한다. 끝까지 실패하면 "AI 모델이 일시적으로
  혼잡합니다. 잠시 후 다시 시도해주세요."로 안내한다.
- 동작 원리: LLMClient.chat의 재시도 루프와 _friendly_error 매핑.
- 관리자 가시성: 3회 재시도 후에도 실패하면 그 세션의 raw 오류·종류·원인이 9.3의
  AI 로그 페이지에 기록·표시된다(`_classify_error` → `llm_errors[]`). 사용자에겐 친절
  메시지만 나가지만 관리자는 실제 원인(503/429/404 등)을 확인할 수 있다.

### 12.2 다크 모드 정원 이름 가독성

- 사전 조건: 3.1과 10.1 수행 후 진행해 주세요.
- 확인 포인트: 다크 모드에서 정원 뷰의 식물 이름이 밝은 하늘 배경에 묻히지 않고
  또렷하게 보인다.
- 동작 원리: 식물 이름에 테마 독립적인 어두운색 + 흰색 halo를 적용했다.

### 12.3 브리핑 최신성

- 사전 조건: 3.1로 식물을 만든 뒤 진행해 주세요.
- 확인 포인트: 홈/캘린더의 "AI 일정 제안" 브리핑이 현재 식물 수를 정확히 반영한다
  (식물을 추가하면 다음 조회에서 바로 반영).
- 동작 원리: 브리핑을 매 호출 재생성한다(과거에는 하루 단위 캐시로 옛 값이 남았음).

### 12.4 AI 응답 마크다운 렌더링

- 사전 조건: 3.1처럼 AI에게 목록·강조가 섞인 답을 유도(예: "내 식물 현황을 항목별로
  정리해줘")한 뒤 진행해 주세요.
- 확인 포인트: AI 응답의 `**굵게**`, `### 제목`, `- 목록`, 줄바꿈이 raw 텍스트가 아닌
  서식으로 렌더링된다. 같은 답을 `/history`(대화 기록)에서 다시 열어도 동일하게 보인다.
- 동작 원리: `frontend/lib/markdown.tsx`의 자체 렌더러를 ChatPanel과 /history가 공유.
  AI가 한 줄로 flatten한 출력도 `normalizeMarkdown()`이 블록으로 승격한다. 링크의
  `javascript:`/`data:` URI는 `safeHref()`가 차단한다.
- 회귀 주의: `react-markdown`은 Turbopack dev 런타임에서 로드 실패하므로 재도입 금지.

## 부록 B. 스킬 - 스코프 권한 매트릭스

대상은 "기존 항목의 수정·삭제"다. 생성·조회는 모든 스코프에서 허용된다.

- 봉우리 수정·삭제(update_bud_progress/status, set_deadline, harvest_bud, abandon_bud):
  - global: 허용
  - plant(해당 식물): 허용 / plant(다른 식물): 거부
  - bud(해당 봉우리): 허용 / bud(다른 봉우리): 거부
  - calendar: 거부
- 식물 삭제(delete_plant):
  - global: 허용 / plant(해당 식물): 허용 / plant(다른 식물): 거부 / bud, calendar: 거부
- 일반 일정 수정·삭제(update_calendar_event, delete_calendar_event):
  - global: 허용 / calendar: 허용 / plant, bud: 거부

거부 시 스킬은 forbidden을 반환하고, 프롬프트 규칙에 따라 AI는 적절한 세션으로의
변경을 권유한다.
