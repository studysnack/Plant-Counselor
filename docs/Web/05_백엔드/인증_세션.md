# 인증과 세션

> 최종 점검: 2026-06-02

관련 문서: [[API_엔드포인트]], [[아키텍처_개요]]

## 현재 모델

인증은 Supabase Auth Google OAuth가 담당한다. 프론트의
`@supabase/supabase-js`가 세션을 localStorage에 보관하고 자동 갱신한다.

커스텀 `/auth/signup`, `/auth/login`, `/auth/refresh`, `/auth/logout` API와
HttpOnly refresh 쿠키는 현재 코드에 없다.

## 브라우저 흐름

1. 사용자가 `/login`에서 Google 로그인을 시작한다.
2. Supabase OAuth 콜백이 완료되면 브라우저가 세션을 복원한다.
3. 프론트 API 클라이언트가 access token을 `Authorization: Bearer ...`로 보낸다.
4. 로그아웃은 `supabase.auth.signOut()`으로 처리한다.

OAuth callback 중에는 PKCE code 교환 전에 초기 세션 이벤트가 null로 올 수 있다.
앱 레이아웃은 URL에 callback code 또는 access token이 있으면 즉시 `/login`으로
돌려보내지 않고 `SIGNED_IN`을 기다린다.

## 백엔드 검증

`backend/app/deps.py`의 `require_user()`가 Bearer JWT를 검증한다.

1. Supabase JWKS를 가져와 ES256 또는 RS256 검증을 시도한다.
2. 실패하고 legacy JWT secret이 있으면 HS256 검증을 시도한다.
3. JWT의 `sub`를 사용자 ID로 사용해 `profiles`를 조회한다.
4. 프로필이 없으면 JWT 이메일과 메타데이터로 fallback 생성한다.

관리자 API는 `require_admin()`을 추가로 사용한다. 프론트 가드는 보조 수단이며
백엔드 검사가 실제 권한 경계다.

## Next.js proxy

`frontend/proxy.ts`는 pass-through만 수행한다. Supabase 세션이 localStorage에 있어
서버 측 proxy가 로그인 여부를 판단할 수 없기 때문이다. 쿠키 기반 redirect를 다시
넣지 않는다.

## 보안 주의

- `SUPABASE_SERVICE_ROLE_KEY`는 백엔드에만 둔다.
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`는 브라우저 공개용 anon 키다.
- 사용자별 Gemini API 키는 Fernet으로 암호화해 저장한다.
- 프론트 인증 가드만 믿지 않고 모든 보호 API에 `require_user` 또는
  `require_admin`을 적용한다.
- Bearer 헤더가 없거나 유효하지 않으면 백엔드는 401을 반환한다.
